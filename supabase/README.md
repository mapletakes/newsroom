# Database migrations

`supabase/schema.sql` — one hand-maintained file, run manually in the SQL
editor whenever it changed — is retired as of `20260909182636_baseline.sql`.
Its exact content (comments and all) lives on unchanged as that migration;
every schema change from here on is a new file in `supabase/migrations/`,
applied through the Supabase CLI.

## One-time setup (do this once, against the existing project)

The baseline migration is a *record* of what's already in production, not
something to execute — production already has every table/column/function
in it. Running it as a normal migration would try to `create table` things
that already exist. Instead:

```bash
# Point the CLI at the existing project (find <ref> in the Supabase
# dashboard's project settings, or in the project's API URL).
npx supabase link --project-ref <ref>

# Mark the baseline as already applied, without running it.
npx supabase migration repair --status applied 20260909182636

# Now push the migrations that come after it — right now, just the one
# adding queue_overview() (see app/api/queue/route.ts for why).
npx supabase db push
```

After that, `supabase migration list` should show both migrations as
applied on both local history and the remote project, and you're on the
normal workflow below.

## Adding a schema change from here on

```bash
npx supabase migration new <short_description>
# edit the generated supabase/migrations/<timestamp>_<short_description>.sql
npx supabase db push
```

Write migrations the same way the existing ones read: comment *why*, not
just what, the same as the rest of this codebase. A migration file is
permanent once pushed — to change your mind, write a new migration that
alters or reverts it, don't edit an old one in place.

## Submission enrichment migration

Apply `20261013200000_submission_enrichment.sql` before deploying the asynchronous
approval code. Existing summaries are marked complete; approved items without
a summary are queued for processing when their channel is viewed. This can
invoke paid AI calls on the existing approved backlog. Review that backlog and
AI configuration before rollout. The migration does not process pending items.

The schema addition is compatible with the previous application version, so an
application rollback can leave it installed. Recovery has a five-minute lease
and a batch limit of three; queue reads and authenticated daily cleanup resume
interrupted work. Provider failures require a manual retry.

For an isolated database with all migrations applied, run:

```bash
psql "$TEST_DATABASE_URL" -v ON_ERROR_STOP=1 -f supabase/tests/submission_enrichment.sql
```

The test inserts fixture rows inside a transaction and rolls them back. Use a
test database rather than the linked hosted project.

`supabase/config.toml` is the CLI's project config, generated by
`supabase init`; `[db].major_version` should match the project's actual
Postgres version (`show server_version;` on the remote database) if it
ever drifts from the default. Nothing here requires the local dev stack
(`supabase start`, Docker) — the app talks to the hosted project directly,
the CLI is only used for `migration`/`db push`/`link`.

## Play-history and export migration

Apply `20261014003000_play_history_exports.sql` before deploying the matching
application code. It adds transactional play-note triggers, per-note export
receipts, and a lease for Discord posts. It does not depend on the approval
enrichment migration.

Review the legacy history before rollout: duplicate linked notes and notes
whose linked submission is no longer played are marked cancelled, with their
contents retained. Detached notes from cleared submissions remain active.
Existing Markdown and Discord timestamps seed their respective receipts.

The application no longer inserts a separate note after a play update. The
triggers must be installed for each successful play to include its note.
Reverting only the application also restores the old timestamp-based export
readers; exports made by that old code do not maintain the new note receipts.
Reconcile those receipts before upgrading again rather than assuming an
application rollback preserves the new export guarantees.

For a test database with all migrations applied:

```bash
psql "$TEST_DATABASE_URL" -v ON_ERROR_STOP=1 -f supabase/tests/play_history_exports.sql
```

The fixture transaction rolls back. Do not run it against the linked hosted
project.
