# Database migrations

`supabase/schema.sql` — one hand-maintained file, run manually in the SQL
editor whenever it changed — is retired as of `20260909182636_baseline.sql`.
Its exact content (comments and all) lives on unchanged as that migration;
every schema change from here on is a new file in `supabase/migrations/`,
applied through the Supabase CLI.

## One-time setup (do this once, against the existing project)

The baseline migration is a *record* of what's already in production, not
something to execute — production already has every table/column/function
in it. Running it as a normal migration would try to `create table` things
that already exist. Instead:

```bash
# Point the CLI at the existing project (find <ref> in the Supabase
# dashboard's project settings, or in the project's API URL).
npx supabase link --project-ref <ref>

# Mark the baseline as already applied, without running it.
npx supabase migration repair --status applied 20260909182636

# Now push the migrations that come after it — right now, just the one
# adding queue_overview() (see app/api/queue/route.ts for why).
npx supabase db push
```

After that, `supabase migration list` should show both migrations as
applied on both local history and the remote project, and you're on the
normal workflow below.

## Adding a schema change from here on

```bash
npx supabase migration new <short_description>
# edit the generated supabase/migrations/<timestamp>_<short_description>.sql
npx supabase db push
```

Write migrations the same way the existing ones read: comment *why*, not
just what, the same as the rest of this codebase. A migration file is
permanent once pushed — to change your mind, write a new migration that
alters or reverts it, don't edit an old one in place.

`supabase/config.toml` is the CLI's project config, generated by
`supabase init`; `[db].major_version` should match the project's actual
Postgres version (`show server_version;` on the remote database) if it
ever drifts from the default. Nothing here requires the local dev stack
(`supabase start`, Docker) — the app talks to the hosted project directly,
the CLI is only used for `migration`/`db push`/`link`.
